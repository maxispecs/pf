# pf (pulpfixer v2)

`pf` is a developer CLI for any repo, in any language: one menu (`pf`) and unified commands (`pf dev`, `pf build`, `pf ver`, ...). It replaces the legacy `pulpfixer` 1.x package and owns the `pf` binary. Published to the cellars registry (`https://cellars.staging.pangenea.com/`) as `pulpfixer`.

## Monorepo

pnpm workspace, twenty published packages (versioned together by `versions.json`, published to cellars) and one private docs site:

- `packages/kit` (`@pulpfixer/kit`): shared foundation. detect, exec, ui, config, util, context and the `Command` / `Plugin` types. Import it by subpath (`@pulpfixer/kit/ui/text`). Depends on nothing.
- `packages/plugin-aws` (`@pulpfixer/plugin-aws`): the AWS plugin. Depends only on kit.
- `packages/plugin-yubikey` (`@pulpfixer/plugin-yubikey`): the YubiKey plugin (`pf otp`, `pf yk`, wrapping `ykman`). Depends only on kit.
- `packages/plugin-io` (`@pulpfixer/plugin-io`): the IO base: adapters and **pipes**. The contract and its registry live in kit (`kit/src/io.ts`: `IoAdapter` with optional `source(config, io)` -> `IoSource { batches(), close() }` and `sink(config, io)` -> `IoSink { write(batch), close(ok) }`, `IoContext { ctx, dryRun, log, batchSize }`, `IoRef` / `ioRef`, `validateIoAdapter`, `registerIoAdapters(adapters, origin)`, `ioAdapter(id)`, `ioAdapterOrigin`; the registry sits on `globalThis` under `Symbol.for('pulpfixer.io.v1')`, like the db one, because every registry plugin installs its own kit). Rows stream as async iterables of batches (`DEFAULT_BATCH_SIZE` 500). `flow.ts` is the chain (`from`, `fromRows`, `concat`; lazy and single-use: `map` / `filter` / `flatMap` / `tap` / `pick` / `omit` / `rename` / `take` / `batch` / `rows` / `to(...sinks)` / `collect` / `count`), `run.ts` is `runPipe` (resolve adapters, a missing one says `pf plugin install io-<id>`; show reads and writes; confirm unless `--dry-run` / `--yes` / every output `harmless`, no TTY refuses; open sources then sinks; run the body; close sinks with `ok` (a failing commit makes later sinks discard), then sources; row counts on stderr; the handles a pipe gets have no-op `close`), `define.ts` is `definePipes({ name, summary, pipes })` -> `pf <name> [pipe] [--param v] [--dry-run] [--yes] [--batch-size n]` (a `PipeDef` is `summary`, `params`, `inputs` / `outputs` as an object or a function of the params, and `transform` or `run`, never both; without `run` it copies its one input to every output; exit 2 usage, 1 failure or declined; an error with a `hint` property prints the hint). Built-in adapters: `memory` (`adapters/memory.ts`, harmless; a sink adds its rows only on `close(true)`), `stdout` (`adapters/stdout.ts`, harmless; `ndjson` / `csv` / `table`). `pf io [adapters] [--json]` lists adapters with where each came from. `src/api.ts` is what pipe packages import (`/api`). Depends only on kit. **No agent or MCP tools for IO or pipes** (rows can hold user data). Docs: `packages/docs/content/plugins/io.mdx`.
- `packages/plugin-csv` (`@pulpfixer/plugin-csv`): the CSV plugin: `src/adapter.ts` is the `csv` adapter (`csvSource` / `csvSink`: streaming parse with header / delimiter / columns, `-` is stdin / stdout; the sink writes a temp file next to the target and moves it into place on `close(true)` (`create` is no-clobber, `overwrite` keeps the mode, `append` copies the target first), nothing on a dry run or `close(false)`), `src/commands/csv.ts` is `pf csv show|columns`. The parser and encoder are in kit (`kit/src/csv.ts`: `CsvParser`, `parseCsv`, `toCsv`, `cellText`; plugin-db's `--csv` output uses them too). Cells are text. Depends only on kit. Docs: `packages/docs/content/plugins/csv.mdx`.
- `packages/plugin-pdf` (`@pulpfixer/plugin-pdf`): the PDF plugin, hand-written with no dependencies and "standard" on purpose: it reads unencrypted PDFs (no OCR, encrypted files are refused with a hint) and writes the standard Helvetica / Times / Courier fonts, Latin-1 only (a character outside it becomes `?` and is counted). Reader (`src/read/`): `lexer.ts`, `filters.ts` (Flate with predictors, ASCIIHex, ASCII85, LZW, RunLength; image filters are unsupported), `document.ts` (`PdfDocument`: xref tables and streams with the `/Prev` / `/XRefStm` chain, object streams, rebuild-by-scan on a broken file; the trailer and xref are parsed with `allowRefs` on), `fonts.ts` (encodings, `/Differences`, `ToUnicode` CMaps, Type0 widths), `content.ts` (the content stream interpreter -> `TextItem`s), `layout.ts` (items -> lines by baseline), `extract.ts` (`PdfFile`, `openPdf`, `parsePageRange`, info, dates, AcroForm fields). Writer (`src/write/`): `serialize.ts` (objects, xref, Flate streams), `doc.ts` (`PdfDoc`: absolute drawing plus a flow cursor with page breaks, `paragraph` / `heading` / `lines` / tables, `onEachPage` hooks that run at `finish()` so the page count is known); `metrics.ts` has the font widths. Templates (`src/templates/`): a `PdfTemplate` is `{ id, options?, start?, write, finish? }` over a `TemplateContext` (`doc`, `options`, `state`, ...); built in `text`, `lines`, `table`, `records` (`builtin.ts`); JSON layouts (`json.ts`, schema 1, strictly validated, unknown keys refused, blocks and `{{placeholders}}` only, never code); `resolve.ts` finds a template by object, built-in id, path, or saved name in `pfHome()/pdf/templates/<name>.json`; `render.ts` is `PdfRenderer` / `renderPdf`. `src/adapter.ts` is the `pdf` IO adapter (source `extract`: `lines` default, `pages`, `items`, `text`, `meta`, `fields`; sink renders in memory and commits on `close(true)` through a temp file next to the target, `create` no-clobber / `overwrite`; a dry run still renders), `src/commands/pdf.ts` is `pf pdf info|text|show|write|templates` (`templates new` saves a starter layout). `src/api.ts` is what pipe packages import (`pdfSource`, `pdfSink`, `definePdfTemplate`, `PdfDoc`). Registers with `api: 3` and `ioAdapters`. **No agent or MCP tools** (PDFs can hold user data). Depends only on kit. Docs: `packages/docs/content/plugins/pdf.mdx`.
- `packages/plugin-db` (`@pulpfixer/plugin-db`): the database plugin (`pf db`, the `sql` / `Db` helpers, `defineQueries`). Depends only on kit. Exports `.` (the `Plugin`, `dbPlugin`) and `./api` (what query and pipe packages import). `src/io.ts` is the `db` IO adapter (`dbAdapter`, `dbSource({ connection, query })`, `dbSink({ connection, table })` or `dbSink({ connection, write(db, rows) })`): a source opens the connection read-only and streams through `Db.stream(query, batchSize)` (a driver's optional `DbSession.stream`, else the result is buffered and sliced); a sink holds one transaction open for the whole pipe (committed on `close(true)`, rolled back on `close(false)`, `insertChunks` groups rows by column set and at most 30000 values); under `--dry-run` it uses the `dry` policy and no transaction. `parseParams` lives in kit now (`kit/src/params.ts`). SQLite is built in: `src/drivers/sqlite.ts` (`node:sqlite`, imported on connect, so pf still starts below Node 22.13), listed in `BUILTIN_DRIVERS` (`src/drivers/index.ts`) and carried as `dbPlugin.dbDrivers`, which core registers at startup with the other built-in plugins; `pf db drivers` shows it as `built in`. Any other driver is a *registry plugin* that default-exports `{ name, api: 2, commands: [], dbDrivers: [DbDriver] }`; the contract and the registry live in kit (`kit/src/db.ts`: `DbDriver`, `ConnectionForm`s that tell `pf db add` what to ask, `makeSession` for transactions, `registerDbDrivers` / `dbDrivers`). The registry sits on `globalThis` under `Symbol.for('pulpfixer.db.v1')` because every registry plugin installs its own copy of kit; core's loader registers a plugin's `dbDrivers` when it loads (`registerPluginDrivers`, `validatePlugin` demands `api: 2` for them), and `PLUGIN_API` is 3 (`ioAdapters` needs `api: 3`, `dbDrivers` `api: 2`; `registerPluginContributions` in `pulpfixer/src/plugins/loader.ts` registers a plugin's db drivers and IO adapters, with the origin `built in` or `plugin <name>`). Connections: `~/.pf/db/connections.json` (0600; driver, form, plain values and only a `SecretRef` per secret field: `keychain` / `env:NAME` / `prompt`, never the value, `store.ts`, `secrets.ts`). A secret is never taken from a flag. Queries: `sql` tagged template (values are bound parameters, `sql.id` quotes names, `sql.raw` is the only text insert; `sql.ts` pure, `compile(fragment, dialect)`), `Db` (`client.ts`: `all` / `one` / `value` / `exec` / `insert` / `update` / `deleteFrom` / `transaction`; update and delete need a where; `WritePolicy` `allow` / `deny` / `dry` follows the method, not the SQL text), `defineQueries` (`define.ts`: one command per query package, `--db`, `--json` / `--csv`, a `writes: true` query confirms and honors `--dry-run`, any other query cannot write). No agent or MCP tools for databases (results can hold user data). A new database with its own protocol client (no npm dependency) is a `packages/db-<name>` plus a line in `KNOWN_DRIVERS` (`plugin-db/src/drivers/index.ts`), `scripts/build.mjs`, `scripts/release.mjs` (`ORDER`) and `pnpm ver init`; one with no dependencies can be a file in `plugin-db/src/drivers/` and a line in `BUILTIN_DRIVERS`.
- `packages/db-postgres`, `packages/db-mysql`, `packages/db-dynamodb` (`@pulpfixer/db-<name>`): the database drivers published on their own. None has an npm runtime dependency. `db-postgres` is a hand-written PostgreSQL protocol (v3) client on `node:net`, `node:tls` and `node:crypto` (`config.ts` the params form and `postgres://` DSN with `sslmode` / socket host / `connect_timeout`, unknown DSN parameters are errors; `protocol.ts` messages, framing and `PostgresError`; `auth.ts` MD5 and SCRAM-SHA-256, the server signature must verify; `types.ts` text-format values decoded by type OID the way node-postgres did, int8 / numeric stay strings; `connection.ts` the socket, TLS answer byte, one queued statement at a time through Parse / Bind / Describe / Execute / Sync; it refuses COPY; tests run against a scripted fake server in `tests/fake-server.ts`, `PF_TEST_PG_URL` adds a live run). `db-mysql` is a hand-written MySQL / MariaDB protocol client on `node:net`, `node:tls` and `node:crypto` (`packet.ts` framing, `protocol.ts` messages, `auth.ts` + `ed25519.ts` the `mysql_native_password` / `caching_sha2_password` / `client_ed25519` plugins, `types.ts` row and parameter types, `connection.ts` the socket; a query with values is a server-side prepared statement, one without is a text query; it never offers LOCAL INFILE or multi statements; tests run against a scripted fake server in `tests/fakeserver.ts`, `PF_TEST_MYSQL_URL` adds a live run). `db-dynamodb` is a hand-written DynamoDB client (dialect `dynamodb`, PartiQL through `ExecuteStatement`; `sigv4.ts` SigV4 on `node:crypto`, checked against AWS's get-vanilla vector; `credentials.ts` keys form, `AWS_*`, static keys in `~/.aws/credentials`, then `aws configure export-credentials` for SSO / assume-role, cached in memory and refreshed a minute before expiry, a profile name is validated because it becomes a CLI argument; `values.ts` JS <-> attribute values, numbers stay exact; `client.ts` `node:https` JSON protocol, an `http:` endpoint only for loopback, pages followed, `maxItems` is an error not a cut, only throttling and one expired-token answer are retried, never a 5xx; `index.ts` the driver and its own session: no BEGIN / COMMIT, `transaction()` queues writes into one `ExecuteTransaction`, a read in it is an error; tests run against a signature-verifying fake in `tests/fake-dynamo.ts`, no live run). `Db.insert` on this dialect uses `insertItem` (`INSERT INTO t VALUE {...}`, one item, no RETURNING). Not a dependency of core: `pf db` installs a `KNOWN_DRIVERS` one when it is needed (picked or named in `pf db add`, a connection being tested, `pf db install <name>`) through the installer core registers in kit (`setDbDriverInstaller` / `dbDriverInstaller` in `kit/src/db.ts`, set in `cli.ts` to `installDbDriver` in `pulpfixer/src/plugins/manage.ts`, which runs `pf plugin install db-<name>` and `loadInstalledPlugin`), or users `pf plugin install db-<name>` (`@pulpfixer/db-*` is unpinned like a preset: `isPreset` in `release.mjs` and `pulpfixer/src/devcycle.ts`). They hold no secrets.
- Query packages (`@pulpfixer/query-<name>`) live in other repos, depend on `@pulpfixer/plugin-db` (`/api`) and hold the actual queries. `pf template apply query-package <name>` creates such a repo (below: `packages/template-query-package`), and the bundled `query-package` skill guides the agent that fills it in. `pf plugin install query-<name>` installs `@pulpfixer/query-<name>` (`candidatePackages` in `pulpfixer/src/plugins/registry.ts`: these names only ever come from the `@pulpfixer` scope). Cellars treats the `@pulpfixer/query-` prefix as a clearance project prefix, so such packages are restricted and a user without clearance gets a 404 (the install message says so). Docs: `packages/docs/content/plugins/db.mdx`, `writing-a-query-package.mdx`.
- Pipe packages (`@pulpfixer/pipe-<name>`) live in other repos, depend on `@pulpfixer/plugin-io` (`/api`) and the adapters they use (`plugin-db/api`, `plugin-csv/api`), and hold scripted IO (`definePipes`). `pf template apply pipe-package <name>` creates such a repo (`packages/template-pipe-package`), the bundled `pipe-package` skill guides the agent. `pf plugin install pipe-<name>` installs `@pulpfixer/pipe-<name>`; like `query-`, `pipe-` is a cellars clearance prefix (`isClearancePackage` in `registry.ts` covers both). IO adapter add-ons (`@pulpfixer/io-<name>`, kit only) are open, not clearance: `pf template apply io-adapter <name>` (`packages/template-io-adapter`), the bundled `io-adapter` skill; the plugin default-exports `{ name: 'io-<name>', api: 3, commands: [], ioAdapters: [adapter] }`. `@pulpfixer/io-*` is unpinned like a preset. Docs: `writing-a-pipe-package.mdx`, `writing-an-io-adapter.mdx`.
- `packages/plugin-system` (`@pulpfixer/plugin-system`): the system plugin (`pf sys`: apply configuration presets to apps on this machine, Cursor first). Depends only on kit.
- `packages/preset-cursor` (`@pulpfixer/preset-cursor`): data only (`preset.json`: the standard Cursor extensions and settings). **Not** a dependency of core: `pf sys apply cursor` installs its latest version from cellars into `~/.pf/sys/presets` each time, so it is bumped and published alone (`planBumps` and `scripts/release.mjs` do not drag core along for an `@pulpfixer/preset-*` package). Another preset is another `packages/preset-<name>` plus an `ORDER` entry in `scripts/release.mjs`.
- `packages/suite` (`@pulpfixer/suite`): data only (`suite.json`): the pulpfixer suite, a list of **features** (`id`, `summary`, `preset`, `packages` = `@pulpfixer/ext-<name>` extension packages, `optional`). `cursor` is the default feature (the `cursor` preset plus Background Tone), `obsidian` is `optional`. `pf suite` lists them and `pf suite enable [<feature>...]` applies them: with no name only the non-optional ones (the install one-liner), an optional one only when named or picked. Not a preset (`validateSuite` in `plugin-system/src/suitefile.ts`; `fetchSuite` installs `@latest` into `~/.pf/sys/presets`, cached copy offline). Published alone, not pinned by core (`isPreset` special-cases `@pulpfixer/suite`). `pf sys apply|diff suite` still works as an alias. `pf suite config [get|set|unset <key> [<value>]] [--json]` manages the suite's **settings** (`kit/src/suite-settings.ts`, user config `plugins.suite` in `~/.pf/config.json`): `reposDir` (default `~/dev`, `PF_REPOS_DIR` overrides) is where **new repos** go, used by `pf template apply` (unless `--dir`, relative to the cwd) and `pf wb-promote --repo`. A new suite setting is one entry in `SUITE_SETTINGS`.
- `packages/preset-obsidian` (`@pulpfixer/preset-obsidian`): data only (`preset.json`, `"app": "obsidian"`, an `obsidian` section: `app` / `appearance` / `corePlugins` / `communityPlugins` / `hotkeys` / `pluginSettings.<id>`), mimicked from a real vault minus per-vault values (icon assignments, export title and path, graph and workspace layout, `sync`). Applied by `pf suite enable obsidian` to one vault (`--vault <path|name>` or a picker over Obsidian's `obsidian.json`; `PF_OBSIDIAN_DIR` overrides Obsidian's folder). **Config only**: pf never installs or downloads a plugin or theme, it enables and configures the ones the vault already has and lists the rest. Same rules as a preset (published alone, not pinned by core).
- `packages/template-query-package` (`@pulpfixer/template-query-package`): data only, the template `pf template apply query-package <name>` turns into a new query package repo (`@pulpfixer/query-<name>`). `template.json` (summary, default `dir`, ordered `params` with `prompt` / `help` / `default` / `pattern` / `choices`, `rename`, `next`) plus `files/` (the tree; `_package.json`, `_gitignore`, `_npmrc` are renamed on apply because npm drops or misreads them when it packs). Placeholders: `{{param}}` and `{{version:@pulpfixer/<pkg>}}` (a package bundled with the pf that applies it). The new repo holds `src/index.ts` (`defineQueries` with a `ping` query), a fake-driver test, `AGENTS.md` (the query rules for the agent), the cellars `.npmrc` (`${NPM_TOKEN}`) and `publish:cellars`. Not a dependency of core: `@pulpfixer/template-*` is unpinned like a preset (`isPreset` in `release.mjs` and `pulpfixer/src/devcycle.ts`). Its `files/src` is in `tsconfig.check.json` (dev dependencies `@pulpfixer/plugin-db` / `kit` as `workspace:*` let it resolve), so an API change that breaks the template fails `pnpm typecheck`; `files/tests` run only in a generated repo. Another template is `packages/template-<name>` plus an `ORDER` entry in `scripts/release.mjs`.
- `packages/template-pipe-package` (`@pulpfixer/template-pipe-package`) and `packages/template-io-adapter` (`@pulpfixer/template-io-adapter`): data only, same shape and rules as the query-package template. `pipe-package` params: `name`, `summary`, `input` (`db` / `csv`), `output` (`csv` / `db`), `connection`; the sample `copy` pipe picks its ends at run time from `const INPUT = '{{input}}' as string` (the template has no conditionals), its tests cover all four combinations (render each and run its tests when you change it). `io-adapter` params: `name` (starts with a letter), `summary`; the sample adapter reads and writes JSON Lines files. Both `files/src` and `files/tests` are in `tsconfig.check.json`. `isPreset` treats `template-*` as unpinned.
- `packages/ext-bg-tone` (`@pulpfixer/ext-bg-tone`): the Background Tone extension for Cursor / VS Code, copied from the old `bg-tone-extension` repo and published as one `bg-tone.vsix` (extension id `local.bg-tone`). Two manifests: `package.json` is the npm package (`pf.extension` = `{ id, vsix }`, the version `pnpm ver` bumps), `extension/package.json` is the VS Code manifest (`scripts/package.mjs` stamps the npm version into it and runs vsce; `prepack` and `pnpm build` run it). It targets the VS Code API (`.ts` import suffixes, esbuild bundle), so it is excluded from `tsconfig.check.json` and has its own `typecheck`; its tests (`tests/`) run with the rest. Its settings live in the `bgTone` section of the repo's `pulpfixer.json` (`src/repoConfig.ts` pure, `src/store.ts` file and watcher), with the old `bgTone.*` workspace settings as a read fallback; `showLastAgent` stays a VS Code setting. The Repo Identity card also shows the repo's **featured actions** as codicon buttons (`src/actions.ts` pure: parse `pf actions --json`, validate icons, quote the terminal command; `src/actionsService.ts`: runs `pf actions --all --json`, `bgTone.pfPath` is machine scope, watchers, the `pf: <label>` terminal; the webview only sends an action id and nothing runs in an untrusted workspace; `bgTone.editActions` writes through `pf actions feature|unfeature`, never by editing the file itself). The Source Control **Versions** section (`bgTone.versions`: `view` = the `bgTone.versionsScm` webview view, `card` = a section of the SCM Repo Identity card, `off`) lists `versions.json` with `[+] 1.2 [+]` buttons like `pf v`: `src/versions.ts` is pure (`parseVersionsFile`, `planBump` mirrors the ver CLI's bump and writes the same format, `stackBumpedSinceHead`: a package bump raises the stack minor only once until the next commit, decided statelessly by comparing the stack with `HEAD:versions.json`, `previewBump`, `shortLabels` (rows show the last path segment, more only to tell equal names apart), `versionsState`: the `featured` array of `versions.json` lists those packages first, in order, with bold names; `planFeature` edits that array for the star button, `VersionsService.setFeatured`, same queue and checks as a bump but no `pf ver sync` since no version changes), `src/versionsService.ts` validates the click (target and part against the file, trusted local workspace), writes only `versions.json` atomically, then runs `pf ver sync` (`ActionsService.runPf`) for the manifests and hooks; `media/versions-list.js` is the renderer both pages share. The codicon font is a dev dependency copied into `media/` by `esbuild.cjs` (gitignored). Not a dependency of core: `@pulpfixer/ext-*` is unpinned like a preset (`isPreset` in `release.mjs` and `pulpfixer/src/devcycle.ts`). Another suite extension is `packages/ext-<name>` with a `pf.extension` block, a line in the `cursor` feature's `packages` in `suite/suite.json` and an `ORDER` entry in `scripts/release.mjs`.
- `workbench/` (a pnpm workspace member that is never published: not in `scripts/build.mjs`, `scripts/release.mjs` or `versions.json`): a place for ad-hoc and repeatable tools. `tools/<name>/index.mjs` are permanent and committed (registered as `pf <name>` in `workbench/pulpfixer.json`; `pf wb-new` starts one in `scratch/`, `pf wb-promote` moves it to `tools/`; `pf wb-promote <name> --repo` instead makes it a repo of its own at `<reposDir>/<name>` with a copy of `lib/` (`lib/promote.mjs`: `planRepo` / `writeRepo`; plain node, imports the built kit's `suite-settings`), then `git init` and `pf repo --no-deploy`), `lib/` holds the shared helpers (`tool.mjs` the runner: simulates unless `--live`, logs to `files/<tool>/logs`, older logs are moved to `archive/`, never deleted; `db.mjs` opens a saved `pf db` connection read-only; `guard.mjs` refuses auth / token tables), `files/` holds every tool's inputs, outputs and logs and `scratch/` the one-offs: both exist (a `.gitkeep` each) but their contents are git-ignored because they can hold user data. It depends on `@pulpfixer/kit`, `plugin-db` and `db-dynamodb` as `workspace:*` (the root `pnpm install` links them; run `pnpm build` first). Run `pf` from inside `workbench/` to see its tools.
- `packages/pulpfixer` (`pulpfixer`): the `pf` binary, built-in commands, agent, host mode, skills, install and update. Depends on kit and every plugin (not the presets).

- `packages/docs` (`@pulpfixer/docs`): the documentation site (Nextra on Next.js, port 4400). Private, never published, not part of `scripts/build.mjs`, `scripts/release.mjs` or the core dependencies. `pf docs` (a shortcut for `pf doc`) or `pnpm docs:dev` runs it, `pnpm docs:build` builds it. `amplify.yml` (repo root) hosts it on AWS Amplify as a static export (`pnpm --filter @pulpfixer/docs build:static`, `DOCS_EXPORT=1` in `next.config.ts`, output `packages/docs/out`; app root `packages/docs` in the console). Pages are MDX in `packages/docs/content/` with a `_meta.ts` per folder. **When you change a command, plugin, the agent or host mode, update the matching page.** `pulpfixer/docs/agent.md` and the agent pages under `content/agent/` and `content/plugins/writing-a-plugin.mdx` cover the same material, so change both.

Dependencies point one way: core -> plugins -> kit. A plugin never imports core. Anything a plugin needs from core moves into kit.
Each package exports `source` / `types` / `default` conditions: dev, tests and typecheck run with `--conditions=source` (straight from `src/`), builds and installs use `dist/`. Root `scripts/` hold the cross-package commands (build, test, release, ver, logo, ask).
Registry plugins (user-installed): `@pf-plugins/<name>` packages live in the npm prefix `~/.pf/plugins` (its `package.json` is the remembered list). `packages/pulpfixer/src/plugins/registry.ts` (npm ops, names), `loader.ts` (import at startup in `main()`, failures never stop pf), `manage.ts` (list/install/update/remove, reused by `pf update`) and `commands/plugin.ts`. Plugin commands are appended after every built-in and de-duplicated, so a plugin never shadows a built-in. Core pins kit and the built-in plugins to exact versions and users only update `pulpfixer`, so the release script refuses to publish a dependency without a new core.
New built-in plugin: `packages/plugin-<name>` (copy `plugin-aws`'s package.json and tsconfig), add it to `scripts/build.mjs`, `scripts/release.mjs` (`ORDER`), the `core` dependencies and `packages/pulpfixer/src/plugins/index.ts`, then `pnpm ver init`.

## Conventions

- TypeScript, ESM, strict. Node >= 18. **No third-party runtime dependencies**, the database drivers included: colors, the picker and argument parsing are hand-written. Dev dependencies only (`typescript`, `tsx`, `@types/node`); the packages depend on each other through `workspace:*`.
- Every invocation prints a banner with the version (`pf v2.0`) to **stderr**, so stdout stays pipeable. Do not add output paths that skip it.
- Colors follow `NO_COLOR` / `FORCE_COLOR` (`src/ui/palette.ts`). Anything with a terminal-only mode (the menu, prompts) must fall back to static output without a TTY.
- Never read, print or write a registry token. Only check that an auth line exists. `.npmrc` uses `${NPM_TOKEN}`. The one exception is host mode, which reads secrets with the instance role into a child process's env only, never to disk or output.
- Host mode (`pf host fix`) gives the agent no shell or file tools. Anything that changes the host is a pf host tool, and the MCP server refuses it without `--apply`.
- Commands that run something support `--dry-run`. `pf deploy staging` auto-detects its target. `pf deploy production` runs only a `deploy:production` script or `pulpfixer.json` entry the repo defines (never guessed from platform configs), always asks for confirmation, and needs `--yes` without a TTY. `pf deploy` with no environment (`pf d`) runs staging if the repo has it, else production, else a bare `deploy` (`pulpfixer.json`, a `deploy` script or `./a deploy`; production-like: always asks). A message (`pf d "fix login"`, `-m`) goes only to a target that takes one (`"message": true` in `pulpfixer.json`, or a repo CLI usage that mentions `message`), as one quoted argument. Deploy and publish stand in for each other (`standIn` in `pulpfixer/src/commands/deploy.ts`, which runs both): a repo with no deploy target and no skipped platform but a publish target runs the publish for `pf d` / `pf ds` / `pf dp`, and `pf ps` with no publish target runs the staging deploy (never production or a bare deploy). `pf rp` first links the repo (`pulpfixer.json` `id` to `~/.pf/repos/<id>.json`, `kit/src/repo-link.ts`), then wires a repo's own helper (`./tl d`) through the bundled `deploy-setup` skill and `findDeployHelpers` (`kit/src/detect/helpers.ts`). The agent and MCP tools deploy to staging only.
- Install action: `pf install [local|<to>]` (`pulpfixer/src/commands/install.ts`, targets from `kit/src/detect/install.ts`) runs the repo's own `install:<to>` / `install-<to>` target (`local:install` = `install:local`): `pulpfixer.json`, package.json scripts (root, then workspace packages), composer, local `./a` CLI; never adds `-y`, never asks. With no target it runs a `pulpfixer.json` `install` entry, else `install:local`, else the only `install:*` target (several: picker, exit 2 without a TTY), else the stack's dependency install (`--deps` forces that). `pf install local|<to>` never falls back to dependencies. The plain package.json `install` script is a lifecycle hook, not a target. Shortcuts `pf i` and `pf il` / `pf install-local`; the menu lists one entry per target.
- Shortcuts: a short name for a full command (`pf r` = `pf dev`, `pf i` = `pf install`, `pf il` = `pf install local`, `pf a` = `pf agent`, `pf t` = `pf troubleshoot`, `pf docs` = `pf doc`, `pf rp` = `pf repo`, `pf d` = `pf deploy`, `pf ds` = `pf deploy staging`, `pf dp` = `pf deploy production`, `pf gp` = `pf git push`, `pf g` = `pf repo commit`, `pf ps` = `pf publish staging`, which runs a repo's `publish:cellars` script and always confirms) is one entry in `SHORTCUTS` in `packages/pulpfixer/src/commands/shortcuts.ts`. Extra args pass through to the target. `pf s` / `pf shortcuts` (`commands/shortcutlist.ts`) lists them grouped by their `group`; the menu and `pf list` do not show shortcuts (only a `pf s` hint), and in a repo `entriesFor` (`pulpfixer/src/menu.ts`) puts the entries adapted from the repo first, as one block, ahead of pf's own.
- New command: add `packages/pulpfixer/src/commands/<name>.ts`, register it in `packages/pulpfixer/src/commands/index.ts`, show it in `packages/pulpfixer/src/menu.ts` if it belongs in the menu, add a test.
- Command resolution order is `pulpfixer.json` override, then scripts/targets the repo defines, then stack defaults (`packages/kit/src/detect/`). New stacks go in `packages/kit/src/detect/stacks.ts` with a test in `packages/kit/tests/`.
- PHP (`composer.json`): `dev`/`build`/`test`/`lint` come from composer scripts (`dev serve start`, `test tests phpunit`, `lint cs-check cs phpcs stan phpstan analyse`), else framework and tool defaults (Laravel `artisan`, CakePHP `bin/cake server`, built-in server on `public`/`webroot`; Pest, PHPUnit, Pint, PHP CS Fixer, PHP_CodeSniffer, PHPStan from `vendor/bin`). `pf deploy staging|production` also run a composer script named like the node ones (`deploy:staging`, ...).
- Local repo CLI (`a` + `cli/run` + `cli/commands/**/*.sh`, `# desc:` / `# usage:` headers): `packages/kit/src/detect/localcli.ts`. A command named like a task (`dev`, `build`, `test`, `lint`, `install`/`setup`) is that task's repo script, `deploy:staging` / `deploy:production` are deploy targets (`-y` is added when its usage mentions it, pf already confirmed), and `pf tools [name] [args]` (`pulpfixer/src/commands/tools.ts`) lists and runs the rest.

## Versioning

When a change is made in a module (package), bump that module's minor version before finishing:
`pnpm ver bump <module> minor`. This also bumps the stack minor. Use `major` only for breaking changes.
Never edit versions in manifests by hand. Modules are the packages: `pnpm ver bump packages/pulpfixer minor`, `pnpm ver bump packages/kit minor`, `pnpm ver bump packages/plugin-aws minor`, `pnpm ver bump packages/plugin-yubikey minor`, `pnpm ver bump packages/plugin-db minor`, `pnpm ver bump packages/plugin-io minor`, `pnpm ver bump packages/plugin-csv minor`, `pnpm ver bump packages/plugin-pdf minor`, `pnpm ver bump packages/db-postgres minor` (and `db-mysql`, `db-dynamodb`: alone, core is not bumped for a driver), `pnpm ver bump packages/plugin-system minor`, `pnpm ver bump packages/preset-cursor minor` (alone: core is not bumped for a preset), `pnpm ver bump packages/suite minor`, `pnpm ver bump packages/preset-obsidian minor` and `pnpm ver bump packages/ext-bg-tone minor` (alone too: `@pulpfixer/ext-*` is unpinned), `pnpm ver bump packages/template-query-package minor` (and `template-pipe-package`, `template-io-adapter`: alone, `@pulpfixer/template-*` is unpinned), `pnpm ver bump packages/docs minor` (several targets may share one command; the stack minor rises once). Bump a package only when its own files changed; a core change that depends on a new kit change bumps both.

Publishing: `pnpm release` is always a dry run and publishes every package whose version the registry lacks, in dependency order. `pnpm publish:cellars` publishes without a confirmation prompt. Never publish without the user asking.
