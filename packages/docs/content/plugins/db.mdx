# Database plugin

The built-in `db` plugin gives every database the same shape: saved connections (`pf db`) and one set of helpers to query, insert and update (`sql`, `Db`). It covers relational databases and, through PartiQL, DynamoDB. Each kind of database is a **driver**. SQLite comes with pf; the others are separate plugins you install when you need them:

| Package | Plugin name | Database | Needs |
|---------|-------------|----------|-------|
| built in (`@pulpfixer/plugin-db`) | | SQLite | Node 22.13 or newer (`node:sqlite`); nothing to install |
| `@pulpfixer/db-postgres` | `db-postgres` | PostgreSQL | nothing: pf speaks the PostgreSQL protocol itself |
| `@pulpfixer/db-mysql` | `db-mysql` | MySQL and MariaDB | nothing: pf speaks the MySQL protocol itself |
| `@pulpfixer/db-dynamodb` | `db-dynamodb` | Amazon DynamoDB (PartiQL) | nothing to install: pf speaks the DynamoDB API itself; SSO and assume-role profiles use the `aws` CLI |

On an older Node, pf still runs and lists the SQLite driver; only connecting to a SQLite file fails, and says which Node it needs. The plugin and the drivers hold no secrets, so anyone can install them. Queries that touch company data live in separate packages, see [Writing a query package](/plugins/writing-a-query-package).

```bash
pf db                             # in a terminal: the connections and a menu to add, test, remove, install drivers
pf db add billing --driver mysql  # a connection; the mysql driver installs itself the first time
pf db list                        # list the connections
```

## pf db

```bash
pf db                             # terminal: menu of actions; without one, the same as pf db list
pf db list [--json]               # name, driver, a safe summary, where each secret comes from
pf db add [name] [--driver mysql] [--form dsn] [--<field> value ...] [--secret-from keychain|env:NAME|prompt] [--no-test] [--yes]
pf db remove [name] [--yes]       # also deletes its keychain entries; no name in a terminal: pick one
pf db test [name]                 # connect and run SELECT 1; several connections in a terminal: pick one
pf db drivers                     # built-in and installed drivers, and the ones you can install
pf db install [driver...]         # install @pulpfixer/db-<driver> (same as pf plugin install db-<driver>)
```

In a terminal, bare `pf db` shows the connections and then a menu: add, test or remove a connection, install a driver, show the drivers. After each action it shows the list again, until you pick **Done** (or press esc).

A driver that pf knows (`postgres`, `mysql`) but that is not installed yet installs itself when you need it: when you pick it in `pf db add`, name it with `--driver`, or test a connection that uses it. pf installs `@pulpfixer/db-<driver>` from the registry into `~/.pf/plugins` and uses it at once. `pf plugin remove db-<driver>` removes it again.

### Adding a connection

The **driver** says what to ask. A driver offers one or more *forms*, and each form is a list of fields:

- MySQL and PostgreSQL: `params` (host, port, user, password, database, TLS) or `dsn` (one connection string).
- SQLite: `file` (the file, read-only or not).

In a terminal `pf db add` first asks which driver, listing the drivers you can still install too (picking one of those installs it), then asks for each field of the form you pick, then connects once to check the values. Without a terminal and without `--driver`, the only driver there is (SQLite, until you install another) is used. Without a terminal, give everything as flags. A field's flag is its key in kebab case:

```bash
pf db add billing --driver mysql --host db.internal --user report --database billing --secret-from env:BILLING_DB_PASSWORD
pf db add local   --driver sqlite --path ./data.db
pf db add legacy  --driver postgres --form dsn --secret-from env:LEGACY_DSN
```

The form is chosen from the flags you give (`--host` means `params`); `--form` says it outright. A connection that fails its check is not saved unless you confirm (or pass `--no-test`).

### MySQL and MariaDB

`db-mysql` has no npm dependency: it speaks the MySQL protocol itself, on Node's `net`, `tls` and `crypto`.

- **Logins:** `mysql_native_password`, `caching_sha2_password` (MySQL 8's default; without TLS the password goes RSA-encrypted with the server's key) and MariaDB's `client_ed25519`. Any other plugin is refused by name.
- **TLS** (`--ssl`, or `?ssl=true` in a DSN) always verifies the server certificate against the host name. Add a private CA with `NODE_EXTRA_CA_CERTS`. A server that does not offer TLS is refused, never used in the clear.
- **DSN:** `mysql://user:password@host:3306/database` (or `mariadb://`; percent-encode special characters in the user and password). Only `ssl=true|false` and `ssl-mode=DISABLED|REQUIRED|VERIFY_CA|VERIFY_IDENTITY` are accepted after `?`, and every TLS mode verifies. Any other parameter is an error, so a setting is never ignored silently.
- **Values** go as a server-side prepared statement, bound by the server. A statement without values is sent as plain text.
- **Types:** integers and floats are numbers. BIGINT beyond 2^53 and every DECIMAL are strings, so they stay exact. DATE / DATETIME / TIMESTAMP are local-time `Date`s (a zero date is an invalid `Date`) and TIME is a string. JSON is parsed. Binary columns, BIT and GEOMETRY are bytes.
- pf never offers `LOAD DATA LOCAL INFILE` (a server asking for a file gets nothing) or several statements in one string.

### PostgreSQL

`db-postgres` has no npm dependency either: it speaks the PostgreSQL protocol (version 3) itself, on Node's `net`, `tls` and `crypto`. Values come back as they did with `node-postgres`, so query packages see no difference.

- **Logins:** SCRAM-SHA-256 (the default since PostgreSQL 14; pf also checks the server's proof that it knows the password), MD5 and cleartext passwords, or none (`trust`). Kerberos, GSSAPI, SSPI and client certificates are refused by name.
- **TLS** (`--ssl`, or `sslmode` in a DSN) always verifies the server certificate against the host name. Add a private CA (Amazon RDS, a company CA) with `NODE_EXTRA_CA_CERTS`. `sslmode=require`, `verify-ca` and `verify-full` refuse a server without TLS; `prefer` uses TLS when the server offers it (verified) and plain text when it does not; `disable` and `allow` (and no `sslmode`) never use it.
- **DSN:** `postgres://user:password@host:5432/database` (or `postgresql://`; percent-encode special characters). An empty database is the user's name. A Unix socket is a directory as the host: `?host=/var/run/postgresql` or `postgres://user@%2Fvar%2Frun%2Fpostgresql/db`. Only `sslmode`, `ssl`, `host`, `port`, `application_name` and `connect_timeout` (seconds, default 10) are accepted after `?`; any other parameter (`sslrootcert`, `options`, ...) is an error, so a setting is never ignored silently. The `key=value` form is not supported.
- **Values** are bound by the server (extended query protocol, one unnamed statement per call), in text form: a `Date` goes with its time zone offset, bytes as `bytea`, an array as an array literal, any other object as JSON.
- **Types:** `int2`, `int4`, `oid`, `float4` and `float8` are numbers; `int8` and `numeric` are strings, so they stay exact. `bool` is a boolean, `json` / `jsonb` are parsed and `bytea` is bytes. `date` and `timestamp` are local-time `Date`s and `timestamptz` an exact `Date` (`infinity` is `Infinity`). Arrays of those are arrays. Every other type (`interval`, `time`, `uuid`, `inet`, ...) is its text.
- pf never runs `COPY` (it is refused and the connection stays usable) and runs one statement per call.

### Amazon DynamoDB

`db-dynamodb` has no npm dependency (no AWS SDK): it speaks the DynamoDB JSON API itself over Node's `https`, signs every request with AWS Signature Version 4 on `crypto`, and runs your statements as **PartiQL** (`ExecuteStatement`). Its dialect is `dynamodb`: `?` placeholders and `"double-quoted"` names, so the `sql` helper, `Db` and `defineQueries` work as they do for the other drivers.

```bash
pf db add orders --driver dynamodb --region eu-west-1 --profile acme   # an AWS profile
pf db add local --driver dynamodb --form keys --region local --endpoint http://localhost:8000 --access-key-id test --secret-from env:DDB_SECRET   # DynamoDB Local
```

- **Credentials**, in this order: the `keys` form (an access key id and a secret access key; the secret is stored as a reference like any secret, never from a flag, and temporary credentials with a session token come from the next two sources); for the `profile` form with no profile named, `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`; static keys of the profile in `~/.aws/credentials`; then whatever the `aws` CLI resolves for the profile (`aws configure export-credentials`), which is how SSO, assume-role and `credential_process` profiles work and needs the CLI (the AWS plugin already does). Credentials are kept in memory only and resolved again a minute before they expire.
- **Endpoint:** empty means `dynamodb.<region>.amazonaws.com`. A custom endpoint (DynamoDB Local, a VPC endpoint) must be `https://`, or `http://` for localhost only, and may hold no user, password, path or query, so credentials never travel in clear text or in a URL.
- **Statements** are bound by DynamoDB (`Parameters`). `SELECT` follows every page of the answer. A result over `maxItems` (default 10000) is an **error**, not a silent cut: add a key condition or raise `maxItems`. `ConsistentRead` is on unless the connection turns it off.
- **Writes:** PartiQL changes one item per statement and needs the full primary key. `Db.insert` writes `INSERT INTO "t" VALUE {'a': ?}` (one item per call, no `RETURNING`); `update` and `deleteFrom` need a where, as everywhere. A successful insert or update reports `affected: 1`. A DELETE of a missing item succeeds, so it reports a count only when you add `RETURNING ALL OLD *`.
- **Transactions:** DynamoDB has no interactive transactions. `db.transaction(fn)` queues the writes `fn` makes and sends them as one all-or-nothing `ExecuteTransaction` (at most 100 statements) when `fn` returns. A read inside it is an error, and nothing is sent when `fn` throws.
- **Types:** strings, booleans and null as they are. Numbers are JS numbers when that is exact and strings otherwise (a 20-digit number, a long decimal), so nothing is rounded. Lists and maps are arrays and objects, sets are arrays, binary is a `Buffer`. Going in, a `Date` is an ISO string, a `Set` of strings or numbers a DynamoDB set, and `NaN`, `Infinity` and an empty set are refused.
- **Throttling** (`ThrottlingException`, `ProvisionedThroughputExceededException`) is retried with a short back-off. Other errors, including a 5xx, are not, because the write may already have been applied. An error shows AWS's name and message and never the statement or its values.
- Not covered: `IN (?, ?)` from `sql.list` (PartiQL wants `IN [?, ?]`: write it with `sql.raw`), streams, table administration and scan segments.

### Where secrets live

`connections.json` (`~/.pf/db/connections.json`, mode 0600) holds the driver, the form, the plain values and, for each secret field (a password, a DSN), only a **reference**:

| Source | What it means |
|--------|---------------|
| `keychain` | the OS keychain (macOS `security`, Linux `secret-tool`). The keychain tool asks for the password itself, so it never goes through a command line. Needs a terminal to enter it |
| `env:NAME` | read from an environment variable each time |
| `prompt` | typed (hidden) each time, in a terminal |

A secret is never taken from a flag, and `pf db list` never shows one.

## The query helpers

Query packages (and your own scripts) use `@pulpfixer/plugin-db/api`:

```ts
import { connect, sql } from '@pulpfixer/plugin-db/api';

const db = await connect('billing');
const rows = await db.all(sql`SELECT product, SUM(amount) AS total FROM revenue WHERE period = ${month} GROUP BY product`);
await db.insert('audit', { who: 'pf', what: 'report' });
await db.update('revenue', { checked: 1 }, { id: 42 });
await db.close();
```

`sql` is a tagged template: every `${value}` is a bound parameter, never text. Names go through `sql.id('table.column')`; only `sql.raw(...)` inserts text as it is. `undefined` and bare arrays are errors (use `null`, or `sql.list(values)` inside `IN (...)`). The same code runs on every driver: placeholders (`$1` or `?`) and identifier quoting are chosen from the driver's dialect.

| Method | Does |
|--------|------|
| `db.all(q)` / `db.one(q)` / `db.value(q)` | all rows / the first row / the first column of the first row |
| `db.query(q)` | the whole result (`rows`, `affected`, `insertId`) of a read |
| `db.exec(q)` | run a statement that changes data |
| `db.insert(table, rowOrRows, { returning })` | one `INSERT` for one or many rows with the same columns |
| `db.update(table, set, where)` / `db.deleteFrom(table, where)` | `where` is required: an object (`{ id: 3 }`, `null` is `IS NULL`, an array is `IN`) or a `sql` fragment |
| `db.transaction(async (tx) => ...)` | one transaction: committed on return, rolled back on a throw; nested ones are savepoints |

A statement can also be a plain string (`db.all('SELECT 1')`). `withDb(name, fn)` opens, runs and always closes. `connectWith(driver, form, params)` opens a database from values you hold, without a saved connection. The helpers do not touch the agent: there are no database tools for it, because results can hold user data.

## Writing a driver

A driver is a registry plugin (`@pulpfixer/db-<name>`) that default-exports a plugin with `api: 2` and a `dbDrivers` list. Kit's `@pulpfixer/kit/db` has the contract:

```ts
import { makeSession, type DbDriver } from '@pulpfixer/kit/db';
import type { Plugin } from '@pulpfixer/kit/plugin';

const driver: DbDriver = {
  id: 'mydb',
  label: 'My database',
  dialect: 'postgres',                  // 'postgres' | 'mysql' | 'sqlite': picks placeholders and quoting
  forms: [{ id: 'params', label: 'Host and user', fields: [
    { key: 'host', label: 'Host', kind: 'text', required: true },
    { key: 'password', label: 'Password', kind: 'secret' },   // kept as a reference, handed to connect() resolved
  ] }],
  describe: (form, params) => String(params.host),             // one safe line for lists: no secrets here
  async connect(form, params) {
    const client = await open(params);
    // execute() runs one compiled statement; makeSession adds transactions (BEGIN / COMMIT / savepoints).
    return makeSession(async (q) => ({ rows: await client.query(q.text, q.values) }), () => client.close());
  },
};
const plugin: Plugin = { name: 'db-mydb', api: 2, summary: 'My database driver', commands: [], dbDrivers: [driver] };
export default plugin;
```

pf registers a driver when it loads the plugin, in a registry that every plugin's copy of the kit shares. A driver may have npm dependencies: they install into `~/.pf/plugins` with it. pf's own drivers have none (PostgreSQL and MySQL speak their protocols themselves), and SQLite, built on Node's own `node:sqlite`, is small enough to live inside `@pulpfixer/plugin-db` (`src/drivers/sqlite.ts`) instead of in a package of its own.
