# Getting started

## Install

One line, with Node >= 18 and npm. No token is needed: pf and all its packages are public on the cellars registry.

```bash
[ -w "$(npm root -g)" ] || { mkdir -p ~/.npm-global && npm config set prefix ~/.npm-global && export PATH="$HOME/.npm-global/bin:$PATH" && echo 'export PATH="$HOME/.npm-global/bin:$PATH"' >> ~/.$(basename "$SHELL")rc; }; npm install -g pulpfixer --registry https://cellars.staging.pangenea.com/ && pf setup --yes && pf skill install --all && pf sys apply suite --yes
```

This is the full install: pf, then `pf setup --yes` (the machine), `pf skill install --all` (the agent skills) and `pf sys apply suite --yes` (the pulpfixer suite: the standard Cursor extensions and settings, plus [Background Tone](/plugins/bg-tone)). The suite step needs Cursor on the machine; without it that last step reports so and everything before it is already done.

### Only pf

To install just pf, without the skills and the suite:

```bash
[ -w "$(npm root -g)" ] || { mkdir -p ~/.npm-global && npm config set prefix ~/.npm-global && export PATH="$HOME/.npm-global/bin:$PATH" && echo 'export PATH="$HOME/.npm-global/bin:$PATH"' >> ~/.$(basename "$SHELL")rc; }; npm install -g pulpfixer --registry https://cellars.staging.pangenea.com/ && pf setup
```

Add the rest later with `pf skill install --all` and `pf sys apply suite`.

### What the one-liners do

The first part only runs when npm's global directory is not writable by you (typical with Homebrew's Node: `EACCES ... rename '/opt/homebrew/lib/node_modules/pulpfixer'`). It switches npm to a user-owned prefix, `~/.npm-global`, and puts its `bin` on your `PATH` (`~/.zshrc` or `~/.bashrc`), so the install never needs `sudo` and Homebrew's directories stay untouched. Where the global directory is writable it does nothing. Open a new terminal afterwards, or `source` your rc file. The plain command is `npm install -g pulpfixer --registry https://cellars.staging.pangenea.com/`.

`--registry` applies to this install only, so your default npm registry is left alone. `pf setup` sets the machine up: shell completions, the optional registry auth line and cleanup of the legacy `pulpfixer` 1.x package (its data in `~/.pulpfixer` is left alone). `--yes` accepts every step without prompts, so the full one-liner runs through; the only-pf one asks.

An `NPM_TOKEN` (from the frontend team) is only needed to publish packages or to install private registry plugins.

From a checkout of the repo, the installer does the same and more:

```bash
scripts/install.sh                # latest published version (switches to ~/.npm-global if npm's global dir is not writable)
scripts/install.sh --from-source  # build this checkout, pack its packages and install them globally
scripts/install.sh --plugin jira  # also install a registry plugin (repeatable)
scripts/install.sh --dry-run      # show what would happen
```

One global install brings everything: the `pulpfixer` package depends on `@pulpfixer/kit` and the built-in plugins.

### After installing

The full one-liner already ran the first two steps below (after the only-pf one, they are how you add them). Every step is one command and safe to rerun:

| Step | Command | What it does |
|------|---------|--------------|
| The pulpfixer suite | `pf sys apply suite` | Applies the standard Cursor setup (extensions and `settings.json` values) and installs the suite extensions, today [Background Tone](/plugins/bg-tone) (a per-repo color tint and logo, plus action buttons for the repo). Additive: nothing is uninstalled, your other settings stay, and the old file is backed up first. Shows the plan and asks (`--yes` skips the question and is needed without a terminal, `--dry-run` previews). Reload the Cursor window afterwards |
| Skills | `pf skill install --all` | Installs the registry skills into `~/.pf/skills` (`pf skill available` lists them; `--to claude`, `--to cursor` or `--to agents` puts them where that agent looks). pf also ships a few skills of its own (`pf-repo`, `ship-staging`, `fix-failing`, `deploy-setup`, `troubleshoot`), and `pf update` keeps the `ver` and `pnpm` skills current on its own |
| Check the machine | `pf doctor` | Checks the install, the registry, skills and agents, your config and the repo you are in |
| Plugins | `pf plugin available`, then `pf plugin install <name>` | Optional registry plugins (`@pf-plugins/<name>`) that add commands. The AWS, YubiKey and system plugins are built in |
| Your repos | `pf rp` (in each repo) | Links the repo to this machine, wires pf's versioning and pnpm helpers into it, sets the Background Tone logo and offers the suite install if Cursor lacks it |

The suite and the skills are fetched at their latest version, so these commands also work as the way to bring a machine back to the standard. The Cursor standard on its own (without Background Tone) is `pf sys apply cursor`. Afterwards `pf update` (`pf u`) keeps pf, its plugins, the skills and the suite extensions you have installed current. It updates the `ver` and `pnpm` skills (installing them when missing) and registry skills you already have, but never installs a missing suite extension. See the [System plugin](/plugins/system), [Background Tone](/plugins/bg-tone) and [Skills](/concepts/skills) pages.

## Shortcuts at a glance

Most of what you do day to day is two or three letters. A shortcut is a short name for a full command, and anything you add passes through to it. `pf s` lists them all.

```bash
pf r                  # = pf dev: run the repo, whatever its stack
pf il                 # = pf install local: the repo's own local install target
pf ds                 # = pf deploy staging: finds the target itself
pf d "fix login"      # deploy (staging, else production) with a message
pf gp                 # = pf git push: the primary remote, then the backup remotes
pf ps                 # = pf publish staging: runs the repo's publish:cellars, asks first
pf docs               # = pf doc: run the repo's docs site
pf a                  # = pf agent: the coding agent, with pf's tools
pf t                  # = pf troubleshoot: the agent plus read-only AWS access
pf v                  # = pf ver: list versions, bump them
pf rp                 # = pf repo: hook pf into this repo
pf u                  # = pf update: pf, plugins, skills, suite extensions
```

Every command that runs something takes `--dry-run`, so you can see what a shortcut does first:

```bash
pf ds --dry-run
pf r --dry-run
```

Production is never a surprise: `pf dp` only runs a production script the repo defines, and always asks. The full table, with notes, is on the [Shortcuts](/commands/shortcuts) page.

## First run

```bash
cd ~/code/my-service
pf              # the menu for this repo
pf list         # the same list, static (for scripts and agents)
pf doctor       # check the machine and repo
```

Inside a repo the menu starts with what pf found in it: the resolved `dev`, `build`, `test` and `lint` commands, the docs site, deploy targets and the repo's own commands and tools. pf's own entries (the agent, versions, plugins, ...) follow. Shortcuts are not in the menu: `pf s` lists them. Outside a repo you get a fallback menu (run a skill, about, doctor).

Try a command without running it:

```bash
pf dev --dry-run
pf docs --dry-run
```

## Keep pf current

```bash
pf update --check    # is there a newer version?
pf update            # pf, installed plugins, the ver and pnpm skills and registry skills
pf uninstall         # remove pf from this machine
```

`pf update` also refreshes a repo's copies of the `ver` and `pnpm` helpers when you run it inside one. See [Skills](/concepts/skills#stack-skills-ver-pnpm).

## Set up a repo

Most repos need nothing. To give pf a few hints, or to add your own commands, write a `pulpfixer.json`:

```bash
pf init            # writes pulpfixer.json from what was detected (--dry-run to preview)
pf repo            # hooks pf's pnpm commands and versioning into the repo
```

See [pulpfixer.json](/concepts/pulpfixer-json) and [Tools and repo setup](/commands/tools-and-repo).
